# 协作精审：初评底稿 + GPT 审核与三章深化

只在 cooperative 模式读取。本协议替代独立模式的版本2全量账本要求，但不放宽来源、未知、机制和模型判断纪律。结果标为“协作精审复盘”，不能声称 GPT 对所有内容从零核验。

## 分工与选择

- 初步复盘承担可独立阅读的基础底稿：概览、三路理论与实际、中期节奏、技能概况、用户每次死亡，以及装备/团战/贡献的首轮判断。
- GPT 审核基础底稿，深化装备、团战、贡献三章；更新短总结与最多三条本人对局改进意见。全局博弈由 GPT 形成 gameplan 片段，合并为报告第一章：2—3个赛前博弈点按预计重要程度排列，赛前部分只用阵容、该场补丁机制与开局可知信息，不能照搬初评的赛后结论；每点末尾另作简短实战对照。团战章逐波检验。全局博弈集中出现一次，决定性窗口后不再追加“贯穿全局的博弈”或同义总结。
- 合格基础内容抽查后直接采用；发现重大错误则修正对应章节和受影响的结论，不重写无关内容。没有可用初评、错场、系统性错认身份/机制或大量无证据主张时，隔离底稿，说明原因并退回 standalone；原始证据不足时交付部分复盘，不强行升级。
- 用户明确要求独立复盘或完整重做时遵从。零星旧格式问题先规范化工作副本；不要求重跑付费初评。

## 先省输入，再省输出

原始 JSON 保存为文件，让程序处理，不直接全部回显给 GPT。先读取确定性全局索引、初评正文与证据索引，再按字段/事件获取必要片段。初评的精简“事实”仍是模型陈述，不能替代程序直接从原始 JSON 提取的值。

`scripts/cooperative_review.py prepare` 生成只包含元信息、十人摘要、部分个人曲线采样、完整团队曲线、目标和战斗/击杀/买活/购买索引的工作文件。其中 `curve_samples` 的键为数组下标，必须结合 `sample_times` 解释；`minute_samples` 才是按 `times` 精确对齐的分钟点，null 或未列出的分钟点表示不可得。提供了 `deaths_log` 的来源也会建立死亡索引。索引没有微观位置、精确技能序列或所有个人曲线，不得把没列出的事件视为不存在。每个索引含指回原始对象的位置。独立扫描须跨全时段，并结合缺失字段与采样范围判断，不只看初评选择的几波。

需要补证据时用 `get` 按 JSON Pointer 取原值；输出超过限制时缩小字段范围，不截断 JSON 冒充完整。已有工具能可靠做到相同功能时可以替代。用户只给两份文件也能使用：精简索引由当前执行环境生成，无需用户手工额外制作。

## 审核范围

必查：用于最终胜负解释、严重失误定性、装备建议、贡献/责任排序、本人改进意见的所有重要主张，包括 GPT 新形成的关键判断。不要只按初评自报优先级选择。核验全局博弈的赛前前提与推演逻辑，确认2—3点排序依据是赛前重要性；比赛数据只用于各点末尾的实战对照，实际选择、结果与偏差仍须有证据。

抽查：基础章节的普通过程描述与重复统计。至少每条线检查一个关键统计/事件及理论成立条件；节奏、技能、死亡章节各检查代表条目和所有高风险主张。用户死亡数与逐次列表先用原始记录核对，有争议或影响最终建议的死亡进一步复核。不能把“抽查未发现问题”称为逐条证实。

抽查遇到错值、错时、机制不适用或因果跳跃：扩大到同类主张及依赖它的后续结论；无法修复重要基础错误时退回独立模式。记录实际检查范围，而非只填“完成”。

主张状态为 supported / partial / unsupported / refuted（支持/部分支持/不足/推翻）；处理为 retained / qualified / replaced / removed。非完全支持的主张不能原封不动留在采用章节，需改写、限定或删除。同一问题若出现在多章，所有受影响段落都要同步处理。无可用微观证据时保留局部限制，不凭空填补。

## GPT 三章内容要求

### 装备

执行 equipment-review.md 的判断标准。审查六核路线与四辅助关键功能装，重点写改变战局的装备与取舍，不重抄全部购买记录。六核逐一回答是否该出黑皇杖（包括未买者），双方分别比较三核全出/部分出/阶段性暂缓；解释威胁、职责、替代保护可靠性、时机与机会成本。

保留全部已确认黑皇杖持有者的关键窗口、每代肉山/持盾生命周期和关键买活冲突。出装必要性与已购后的使用效果分开，组件拆卖/重组、送达未知不丢失。

### 团战

全局博弈独立置于报告第一章；本章只用本波具体条件、过程和结果验证相关命题，必要时简短引用，不重复整场计划，也不在窗口后另写全局博弈。每波必须执行 [full-review.md](full-review.md) 中“决定性团战”及其展开要求，同时逐项验收 submission-protocol 的团战验收清单。这两部分为本模式必读，不得用协作模式压缩为几条转折结论。

每波标题前设置唯一 `<!-- review-fight: fight-1 -->` 标记，标题后立即放 full-review 模板规定的参战数据表，再设置“团战分析”“本人本波表现”“本波总结”小节。本人表现必须逐波结合用户英雄实际数据、职责与后果评价，不以初评中的一句总评替代；未参战或参战不明也保留评价边界。编号按波递增或使用其他稳定唯一编号，不能只给部分波次加标记。check/merge 检查各标记下的表格和分析结构；审核者另须核对全部选定波次均已标记、十人身份与统计口径正确。

正文逐波独立展开战前条件、双方计划、开团目标、第一/第二阶段、发动机与保护者、收尾、地图转化、贡献/失误与重打方案，并保留反证。一个核心博弈只限制主命题数量，不限制过程细节或关联因素。无法确认的微观顺序和目标逐项说明。

### 十人职责与贡献/过错

六核与四辅助采用 [full-review.md](full-review.md) 的六核/双辅助标准，以及提交协议的逐人验收清单。六核各写经济进程、对线与补发育、装备与输出对象、技能窗口、死亡/买活/地图转化、团队赋能、职责完成度和同位置比较。四辅助逐人写对线转化、信息/视野、控制救人、关键死亡价值和装备资源匹配。

contribution 片段依次设“天辉”“夜魇”两个小节，各放该阵营五位英雄，按已确认的一至五号位排列；六核与四辅助合计十个独立个人段落，每位英雄一段，标明阵营、英雄、位置与胜负。胜方五人做贡献分析，败方五人做过错分析，逐段执行 [职责评价方法](role-and-gameplan.md#九十人逐段评价胜方贡献与败方过错)，在同一段完成“职责—行为与证据—后果—贡献/过错”的评价链，不另写一轮十人职责或贡献。必要的团队比较仅作简短收束，不重复十段。无证据支持的过错不制造，不能只评价用户阵营。

无需复制独立模式的全量机器账本，但正文必须完整，不能只交十人概览表或只展开重点英雄。严重定性与贡献/责任排序须回查原始证据；用户个人表现按分析要求单独给出关键决策和改进，不能只评价队友。

装备、团战、贡献三个深化片段执行 [深度标准](full-review.md#深度标准从发现问题走到解释选择)：处境、机制、职责与选择、后果、替代代价和反证。六核各有独立过程分析，四辅助各有职责因果解释，十人装备均分析路线和关键取舍；不要求填独立模式全量账本，但正文深度不能因此降低。

基础底稿仍可按既定范围抽查采用；只有标签和结论、缺乏对线理论或过程解释的章节应补写并标为 rewrite，不能只因数值没错就直接采用。战斗经过可引用稳定编号，引用处只增加本章尚未说明的装备或技能判断；已经写明的过程与人物判断不重复改写。重要窗口不凑正反案例。

## 可合并的章节约定

初评与 GPT 替换稿使用独立一行的 `<!-- review-section: ID -->` 标记，后面放正常 Markdown 标题和正文。不把全文包在代码围栏内。稳定 ID 顺序：

gameplan（全局博弈）、summary（一句话结论）、points（本场要点及限制）、lanes（三路）、tempo（节奏）、skills（技能）、deaths（用户死亡）、equipment（装备）、fights（团战）、contribution（十人职责、表现及贡献/过错的统一评价）、training（本人对局改进意见）；初评末尾另有 handoff（重要主张与证据索引，不合入公开报告）。

GPT 必须更新 gameplan、summary、equipment、fights、contribution、training；其余五章可 adopt 或 rewrite。初评可以只提供 gameplan 以外的十个片段；全局博弈由 GPT 核验后写入替换稿。审核文件的 sections.gameplan 须填写 rewrite/rewritten、note 与 evidence，不能只移动标题或复制初评结论。替换稿只输出实际要替换的章节，避免重抄合格正文。初评无标记时，用工作副本添加映射，不更改原始初评；缺章节要补齐或转独立模式，不能空壳补标题。

## 工具与审核记录

先生成工作文件（路径按实际环境替换）：

```sh
python scripts/cooperative_review.py prepare match.json --preliminary preliminary.md --user-account-id ACCOUNT --output cooperative.json
python scripts/cooperative_review.py get cooperative.json --pointer /source_match/teamfights/0
```

脚本不运行模型、不联网、不修改原始文件，输出文件已存在时拒绝覆盖。prepare 同时保存原始 JSON 的稳定摘要与初评文件摘要，仅防止工作材料意外变化；这不证明初评生成时使用了同版 JSON。prompt.sha256 仍只是提示词指纹。

审核文件保持 `dota.cooperative-review.v1`、mode=cooperative：

- `index` 为程序事实索引，不手改；源数据更新时重新生成并回查受影响结论。
- `intake_note` 说明身份、上游版本核验与资料限制。
- `checks` 的 intake、independent_scan、important_claims、global_gameplans 各填具体 note 与 evidence。
- `sections` 各填 action=adopt/rewrite，review=sampled/verified/rewritten，note 与 evidence。“采用”默认 sampled；仅确实全面核验该章节才用 verified。不要重抄章节正文到审核文件。
- `training_items` 保存按优先级排列的1—3条建议，每条填 signal（用户本场具体时点、选择与识别信号）、action（本人更合适的处理）、tradeoff（代价）和 evidence；training 替换稿须与其一致，说明原选择的后果，不写队友改进清单或通用训练计划。
- 通常选择3—5波团战，数量例外须说明原因并交叉检查全时间轴。确实没有决定性团战时，可填写 `fight_selection` 对象：`selected_count=0`、`reason`、`timeline_crosscheck`、`evidence`；正文解释依据，并用实际事件检验全局博弈。空的解析器团战列表本身不足以证明无团战，不能以此跳过分析。
- `claim_audits` 每项填 id、section、claim、verdict、handling、reason、evidence。仅记录重要主张与抽查发现的问题，不给每个普通数值建立长记录；重复主张可合并，但要追踪所有受影响章节。
- evidence 使用与独立脚本相同的 source_type、judgment、refs、limitations；refs 指向 `/source_match/...` 或真实 `/supplemental_sources/...`。未知结论引用能证明限制的实际字段并解释缺口，不伪造缺失字段路径。机制来源以实际页面链接说明，不把网页或模型文字冒充战斗日志。
- 可选真实补充来源按账本规范记录；模型底稿不能放入 supplemental_sources。无需加载整个 ledger-schema.md，脚本没有自动适配任意日志的能力。

```sh
python scripts/cooperative_review.py check cooperative.json --replacements revisions.md
python scripts/cooperative_review.py merge cooperative.json --replacements revisions.md --output final.md
```

合并器保留上述十一个内部章节 ID 和审核边界，最终按照 [提交协议](submission-protocol.md) 的七章节分组：gameplan、summary+points、lanes、tempo+fights、equipment+skills、contribution+deaths、training。审核范围放入“比赛结论与数据边界”，报告以本人改进意见结束，不追加验收段落。只调整标题层级，保留选定正文和代码围栏，移除 handoff，不再次调用 GPT 全文生成。正文中使用稳定事件编号引用，不依赖自动生成的标题锚点；六级标题无法再嵌套时先规范化工作副本。

合并后七章节并不表示审核范围扩大；抽查/采用/重写仍逐个内部片段披露。默认应在当前可执行环境合并；将来服务器可复用该工具，但不能声称本次已部署服务器自动合并或按需取证接口。

合并稿直接呈现完整比赛分析，不添加技能测试或修订说明。合并前检查 tempo、fights 等片段是否含有重复的全局博弈；将必要的全场判断整合进 gameplan，在工作稿中删除重复段落。需要调整采用片段时，将对应章节标为 rewrite 并同步审核记录，保留原始初评。合并后确认“贯穿全局的博弈”等同义内容没有在决定性窗口之后再次出现。合并后检查每波是否有针对用户的本波表现评价，以及六核、四辅助的整场过程与综合判断是否各自只出现一次，删除换标题、改措辞或转成表格后重复的人物评价；检查十人职责与贡献是否被重复输出，用户死亡片段是否重复人物总评，以及残留旧结论、矛盾、重复、缺章、三路理论、黑皇杖必要性、每波核心博弈、贡献与本人改进意见的一致性，以及中文名称和隐私。确认后填写 `final_semantic_check.status=complete` 与具体 note，再运行：

```sh
python scripts/cooperative_review.py check cooperative.json --replacements revisions.md --final final.md
```

返回 COOPERATIVE_REVIEW_COMPLETE 只表示结构/摘要/合并一致性通过且审核者声明完成语义检查，不证明判断正确或 GPT 全量审计。它与独立模式 REVIEW_COMPLETE 不等价；独立验收函数不接受这种审核文件。

不能运行脚本时按相同分工手工建立紧凑审核记录并合并，注明“人工协作验收，未运行机器门禁”。用户要求聊天中输出全文时可照做，但不要声称能同时省去完整输出的 token。缺基础章节、重要主张未处理或三章未完成时输出“部分协作复盘”，不伪装通过。公开发布仍需单独授权与脱敏。
