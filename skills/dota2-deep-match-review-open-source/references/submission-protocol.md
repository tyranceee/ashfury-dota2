# 独立复盘提交与验收

本协议只管理 standalone 的覆盖、出稿和验收。分析方法见 [full-review.md](full-review.md)，字段与保存格式唯一维护于 [ledger-schema.md](ledger-schema.md)。cooperative 使用自己的 [审核协议](cooperative-review.md)，focused 只检查本轮所问问题。

## 状态与完成条件

依次确认数据能力、完成事实与分析记录、通过成稿前检查、核验最终正文。脚本对应 `DRAFT_ALLOWED` 和 `REVIEW_COMPLETE`；机器状态只说明结构与来源引用通过，完整交付还需人工语义检查。

每个必需对象必须有判断和来源。局部细节缺失写明具体原因；整个必需栏目无法形成结论则标为 `limited`，交付部分复盘。带理由的“不适用”仅用于确实不适用的内容，不能把所有字段都填未知来冒充完成。

完成不以字数、段落数或正反案例数量衡量。六核、四辅助与十人装备均须完成过程和职责分析；重大转折与争议进一步深挖。深度标准见 full-review，不能以“普通条目、无争议”缩减必填字段或仅交付结论表。

## 覆盖检查

数量和具体必填字段见 ledger-schema，验收重点是：

- 比赛、补丁、用户身份正确，原始材料与初评身份没有混淆。
- 双方计划与反制有实际事件检验；已独立扫描全时间轴，不只看初评或解析器挑出的团战。
- 三路各有理论、实际和偏差；纯对线、支援及补发育分开；四辅助压制已经检查。
- 十名玩家均有职责、资源与结果判断，六核有同位置比较；用户死亡逐次核对。
- 十人出装均检查；六核黑皇杖必要性及双方配置、所有已确认持有者和每代持盾均有记录。
- 关键技能与决定性团战解释了输出窗口和目标收益；不凑好坏案例，也不把时间先后自动当作因果。
- 输出对象、建筑、肉山和买活已检查；最终贡献/责任与前文一致。
- 本人对局改进意见1—3条，按优先级排序；每条有触发信号、具体动作、重要代价和本场证据。

同一事件在一处展开，其他条目可指向其编号和对应结论。覆盖不等于重复写作；跨章引用不代替原始来源。

## 核心、辅助与团战验收清单

独立与协作的正文均逐项覆盖以下清单；协作按基础章节审核分工执行相同的分析深度。每项应有过程与判断，或明确标明不适用/缺失证据及原因。只在账本写过、不在正文解释，不算完成。

### 每名核心，共六名

- 英雄、位置、理论职责
- 本局首要/次要胜利职责；是持续输出发动机、空间/前排、保护点、控制枢纽或目标转化点中的哪些
- 需要赋能的队友、必须限制的敌方英雄，以及履责成功的可观察信号
- 5/10/15/20/25/30分钟经济；比赛不足该时长时标不适用，超过30分钟则补关键后期节点
- 纯对线结果与对线后补发育
- 核心装备顺序、购买时间、使用次数、针对性与强势窗口
- 参战率、总输出、关键阶段输出、主要输出对象
- 关键技能/BKB如何创造或错过输出窗口
- 团队赋能：是否维持阵型、保护持续输出点、创造第二轮技能时间；不适用或数据不足时说明
- 所有关键死亡及其后果；买活、买活经济与买活战果
- 建筑伤害、Roshan/Aegis参与、团胜后的地图转化
- 职责完成度、最重要贡献、最大失误
- 与对方同位置的明确横向结论

六名核心可以共用一张曲线数据表，但每名核心必须另有一段独立分析，六人共六段；逐段标明身份、胜负及贡献/过错评价，同位置比较不将两人合写。禁止用一张简表和一句总评代替六核审计。

### 每名辅助，共四名

- 对线压制与己方核心发育转化
- 视野、反眼、开雾与信息贡献
- 控制、救人、先反手和关键技能
- 关键死亡逐项判断其战术价值
- 装备与资源是否匹配职责
- 最终职责完成度

四名辅助每人独立一段，共四段，不能按阵营合写成两段。与六核合计十段，胜方五人逐人评估贡献，败方五人逐人评估过错；职责、关键行为、后果与贡献/过错在同一英雄段落内完成，不另写十人贡献或十人职责的重复评估。各段须有职责、过程证据及后果，缺乏过错证据时明确责任边界，不强行给五名败方玩家分锅。

### 每波决定性团战

每波先呈现参战数据表，再设“团战分析”“本人本波表现”“本波总结”三个小节；列名、十人核对与统计口径按 full-review 的逐波模板执行。标题包含本波“天辉 X : Y 夜魇”英雄击杀数并核对统计口径。英雄表格核对是否参战、技能与物品、伤害和击杀/死亡；参战格只填“是/否/无法确认”，不列控制记录与证据限制。治疗列依据原始团战 healing 数据是否可用保留或删除；经济/经验只在团战分析中解释双方总体变化，不逐人列项。以下分析清单须完整执行，不能被表格取代。

- 时间与地点/目标
- 战前经济、经验、装备、BKB、买活、Aegis、兵线和建筑
- 本波核心博弈：只选一个最能解释结果的命题
- 双方在该命题下的合理思路与反制
- 开团方、第一目标、第一轮技能与承伤者
- 第一阶段：控制、爆发、BKB和最先失去战力的人
- 第二阶段：BKB结束后的输出窗口、核心接管或脱节
- 发动机—赋能者关系：谁需要连续输出，谁创造时间和生存条件，这组关系是否被打断
- 收尾：击杀、撤退、追击和存活
- 战后经济/经验变化及Roshan、塔、兵营、基地转化
- 最大贡献、最大失误、关键转折
- 本人英雄的本波关键数据、当时职责、行动与团队后果、履责评价及可行改进；未参战或参战不明也要说明，不能只列数字
- 结果验证：谁赢了本波核心博弈
- 重打一次只修改一个优先级的具体方案
- 博弈思路的事实、模型判断和未知边界
- 反证、替代解释及决策质量；胜利不能单独证明决策正确

阶段概述或一句“某方团灭”不算完成团战复盘。

没有可证实的最大失误或某类过程时明确说明，不制造负面案例；证据充分时不能以避免重复、节省篇幅或一项主博弈为由省略。表格只承载共用数据，不替代每名核心、每名辅助和每波团战的独立分析。

## 默认七章节正文

完整报告使用以下同级标题及顺序。“全局博弈”固定放在第一章，报告标题与比赛身份可放在章前。全局计划全篇集中展开一次，不在决定性窗口后重复“贯穿全局的博弈”或换标题复述同一内容。其他数值原表可留在账本，但每波参战数据表及以上分析清单必须在正文中落实。七章节仅作为外层目录：

| 主题标题 | 主要内容 |
| --- | --- |
| 全局博弈 | 第一章：按重要程度排列2—3个赛前博弈点，分析双方计划、反制、条件与代价，不代入过程数据；每点末尾简短对照实战 |
| 比赛结论与数据边界 | Match ID、用户与胜负、最重要结论、数据能力和影响结论的限制 |
| 阵容与三路对线 | 双方胜利条件与职责；三路理论—实际—偏差；辅助压制与补发育边界 |
| 节奏与关键团战 | 检验第一章博弈的实际事件、经济/经验拐点、关键地图决策与决定性团战；事件主分析放这里 |
| 装备与技能决策 | 十人出装筛查、关键装备取舍、六核黑皇杖必要性与双方配置、关键技能及逐代持盾；引用相关战斗 |
| 十人职责与用户死亡 | 按天辉、夜魇分节，每队五人各自一段，将职责、实际表现、胜方贡献或败方过错合写；包含同位置比较，另核对用户逐次死亡 |
| 本人对局改进意见 | 只针对用户本场表现：具体时间点与选择、后果、更合适的处理、识别信号与代价；1—3条优先意见 |

“节奏与关键团战”下逐波设独立小节；“十人职责与用户死亡”下依次设置“天辉”“夜魇”“用户个人表现与死亡”小节。天辉与夜魇各含五位英雄，每位独立一段，按已确认的一至五号位顺序排列；位置不明时标明限制，不为排序猜位置。六核与四辅助仍按各自分析标准执行，但不再按核心、辅助另外分组或重复评价。用户死亡小节聚焦事件与改进，沿用该英雄已有的综合评价。允许表格和明确的跨章引用。六核各有可独立阅读的过程分析，四辅助各有职责因果解释；不以统一字数衡量，但不能只用一张总表代替正文。表格承载对比和共享统计；六核、四辅助的过程和判断只在各自个人段落完整解释一次，其余位置引用已有内容，不再输出一组过程判断或人物总评。

七章节不是七段短评：按 full-review 的深度标准检查处境、机制、选择、后果、替代代价和反证。不要在结尾再重复整场总结；比赛结论与“十人职责与用户死亡”的责任说明相互一致即可。

旧15章成稿仍可通过兼容结构检查，无需仅为版式重做历史复盘；新稿使用七章节。机器允许标题带编号或补充括号，但所有主题须同级、各出现一次且有正文。协作使用内部十一个章节标记，合并后也输出七章节，详见协作协议。

## 两阶段检查

脚本使用技能目录中的绝对路径，以下是相对技能目录的示例：

```sh
python scripts/extract_match_facts.py --check-ledger ledger.json --stage draft
python scripts/extract_match_facts.py --check-ledger ledger.json --stage final --review-markdown review.md
```

draft 通过且原始证据已核对后组织完整正文；final 重新检查数据、记录、引用、比赛 ID 和正文结构，并逐个核对团战编号、表格及其后的分析与总结。缺任何一波的表格、只有表格没有分析，均不能通过完整交付检查。不能通过改自报数量、模式标签或摘要来绕过错误。原始数据变化时重建提取结果并复核相关分析。

无法运行脚本时按相同覆盖做人工检查，明确“人工验收，未运行机器门禁”。数据不足时可以先交付部分复盘，不必为无法通过完整门禁循环补写。

收到初评时按 [初评接收协议](preliminary-review.md) 另核对关键主张及独立漏项扫描。独立脚本不会自动审核初评的真实性；协作抽查也不得声称全量核验。

## 人工语义验收

交付前集中检查一次：正文是否独立完整，是否混入技能测试、修订或版本更替说明；开篇是否有按重要程度排列的2—3个赛前博弈点，是否把本局过程数据混入赛前推演，实战对照是否独立且简短；全局博弈是否仅在第一章集中出现，决定性窗口后是否残留同名或同义重复段落；六核和四辅助的整场过程与综合判断是否各自只写一次，是否在其他标题、表格或总结下换说法重复；职责与贡献/过错是否合并在同一英雄段落内；是否按天辉、夜魇分节且各覆盖五人；六核与四辅助是否各自一段、共十段，胜方五人是否逐人评估贡献、败方五人是否逐人评估过错且有证据支持；每波表格是否正确对应英雄与窗口、十人是否核对、缺失是否误记为零、表后七阶段分析与总结是否充分，每波是否有结合用户英雄实际数据的“本人本波表现”，且整场人物评价未重复抄写；引用是否支持主张；技能目标、库存与冷却是否超出证据；理论对线是否事后倒推；模型计划是否写成玩家意图；六核及十人装备是否仍有过程分析，结论是否解释了机制和替代代价；章节与账本是否一致；跨章引用是否能定位；中文名称与数值性质是否准确，尤其检查“关键技能与物品”列是否仍残留内部代码名、是否将记录次数误写成命中或成功次数；本人改进意见是否针对用户本场可改变的选择，最后一章是否混入训练计划、团队改进清单或验收内容。

机器不能证明上述语义成立。数据足够但正文只有标签、数字和结论时，应继续分析与重写，不能用“部分复盘”掩盖分析未完成；确因资料缺失无法完成时才说明具体限制。声明完整前必须完成这一步。

## 交付与续写

保存成稿及必要账本/审核记录。聊天默认给结论、限制和文件链接；用户要全文时输出全文。长稿可以连续分段，途中标注“复盘进行中”，最后检查同一份合并稿。

覆盖与检查结果保存在账本或审核记录。影响结论的未解决事项及协作范围在“比赛结论与数据边界”简述，不在报告结尾追加验收摘要。缺项如实列出；不要显示虚假的全部通过。没有用户发布请求时到本地交付为止。
